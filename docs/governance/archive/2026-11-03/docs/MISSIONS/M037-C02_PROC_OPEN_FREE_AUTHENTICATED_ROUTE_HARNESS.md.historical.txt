## Scope

2. Pass authenticated identity through an opaque, one-time context file:
   - random token generated by the root-owned helper;
   - private temporary directory owned by `www-data`, mode `0700`;
   - context file created exclusively by the parent test, mode `0600`;
   - login and entity never appear in argv, environment, helper output, or logs;
   - child consumes and deletes the file before rendering.
3. Preserve aggregate-only diagnostics and external-customer denial coverage.
4. Update release tests, checksum-pinned helper/installer, metadata-free artifact, mission/report/changelog evidence.
5. Install the reviewed helper on canonical `backup-erp` and run `compare`/`preflight` only.

## Architecture and data flow

The helper creates one private in-container context directory and one cryptographically random opaque token per route. It runs the test once in `--issue` mode. That process loads Dolibarr, selects the scoped active user, and atomically creates `<token>.json` without exposing its content. The helper then runs the same test in `--render` mode using only role, route key, and token. The render process validates ownership, mode, size, path, and JSON shape, deletes the context file, establishes the synthetic session, and renders the approved route. The helper verifies consumption and removes the private directory during cleanup.

Standard Dolibarr configuration cannot solve this because the defect is isolated to the release acceptance harness, not Dolibarr runtime behavior.

## Permissions and visibility

- Both PHP invocations run as `www-data`.
- The context directory and file are accessible only to `www-data`.
- The random token is not an authority field and carries no identity by itself.
- User selection retains Dolibarr entity sharing and `fk_soc`/admin scope.
- External customers remain denied from the admin dashboard.
- Raw route output, login, session, SQL, credentials, and customer data must never be printed.

## Database, accounting, and configuration impact

- **Database:** Read-only user lookup during preflight; no writes.
- **Accounting:** None.
- **Configuration/module state:** None.

## Functional requirements

1. The authenticated test source must contain no `proc_open`, `proc_close`, `proc_terminate`, or child pipe launcher.
2. Every context token must be lowercase 64-hex and generated by the helper from the OS random source.
3. Context creation must be exclusive and fail if the file already exists.
4. Render must validate and consume the context before loading the requested route.
5. Context files must not remain after success or failure.
6. The helper must still validate six admin routes, eight customer routes, and one external denial.
7. The current-runtime admin diagnostic must pass before schema snapshot or any mutation-capable command can proceed.
8. Installer rotation must accept only the currently installed reviewed helper hash and the new reviewed helper hash.

## Risks and rollback concept

- **Context leakage:** prevented by `0700` directory, exclusive `0600` file, opaque token, consumption before rendering, and cleanup trap.
- **Replay:** prevented by exclusive creation and deletion before use.
- **Helper rotation error:** checksum-pinned installer accepts only the known old and new hashes.
- **Rollback:** before `apply`, rollback is helper rotation back to the previously installed reviewed helper through a separately pinned installer. No application/database rollback is needed.
