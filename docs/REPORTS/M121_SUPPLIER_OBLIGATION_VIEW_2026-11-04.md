## Behavior and financial boundary

The existing operation supplier workflow now presents separate facts instead of its opaque total/paid/remaining string: native order amount and commitment state, linked invoice total, recorded invoice payments, and remaining after those recorded payments. Human supplier name precedes exact native source references. The existing supplier-owner state resolves the customer/project/order/invoice relation; no new record discovery or guessed link is added. This statement covers one linked operation, not the supplier's full account or every customer project.

The new pure helper in `custom/chinaplanetoperations/lib/supplier_obligation.lib.php` performs no SQL, posting, currency conversion or persistent state change. It reads the existing owner's verified state and native `invoiceSummary()` result; it does not sum marker amounts, independent ledgers, order and invoice amounts, or currencies. Existing payment admission and posting arithmetic are unchanged. A completed task/operation cannot change these financial facts. Customer-funds allocation is a separate attribution and is not inferred from a supplier payment.

Order statuses 1–5 retain the native validated/approved/sent/received commitment classification; draft, cancelled/refused and unknown values receive separate labels. Cancelling an order does not suppress its separately linked invoice. Draft invoices have no displayed payment remainder. Closed invoices with a positive residual, abandoned/unknown status, unsupported invoice type, nonfinite/negative/overpaid amounts, inconsistent residual or raw currency mismatch require native review and display no numeric remaining. A zero residual is shown only when the native recorded payment total actually equals the invoice total in a supported state.

**This is not complete supplier outstanding accounting.** The incumbent `total − recorded invoice payments` calculation omits applied deposits, credit notes and closure adjustments that native `CommonInvoice::getRemainToPay()` also considers. The UI labels this as remaining *after recorded payments* and always displays the EN/AR limitation plus the exact native invoice link for payable review. Recorded invoice payments do not establish bank reconciliation or which customer funded them. No full opening/advance/FX/closing supplier statement, historic as-of reconstruction, automatic credit deduction or settlement policy is introduced.

The only owner read change makes a failed marker SELECT throw an unavailable error instead of returning a false empty workflow. It changes no posting math. Existing supplier read and action gates remain around the new statement; supplier payment references and controls retain their existing restrictions. No public/customer interface is added.
